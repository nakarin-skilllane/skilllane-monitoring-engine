วัตถุประสงค์

  • หน้าที่ developer เปิดเมื่อรู้ว่ามีอะไรผิด: ไล่ log ตามเวลา กรองให้แคบ แล้วเปิดบรรทัดที่พังเพื่อดูว่าแก้ที่ไหน (ข้อ 2 activity log, ข้อ 5 error อ่านง่าย)
  • ทุกแถวมีเวลา ICT ถึง ms, level, service/role และ env อยู่ที่ top bar (ข้อ 1)
  • แถว error ใช้กติกาเดียวกับ components.html ทุกหน้า: หัวข้อ = hint แล้ว chip method, route, status, source (หรือ job), file, target, duration ข้ามตัวที่ไม่มี
  • ใน drawer คัดลอก JSON ดิบและสรุปให้ AI ได้ ชื่อ field ใต้ label คือชื่อคอลัมน์ ClickHouse (ข้อ 4)
  • กราฟแยกเป็นสองกราฟเพราะ INF มากกว่า ERR ประมาณ 450 เท่า: ถ้าซ้อนในแกนเดียว ERR สูงไม่ถึง 1 px

ข้อมูลมาจาก

  • ทั้งหน้า: GET /api/logs ด้วย env, from, to จาก top bar และ q, service, level (comma list), event, userId, route (METHOD /path), category จากแถบตัวกรอง
  • กราฟ, ตัวเลขบน chip level และจำนวนแถวทั้งหมด: histogram[{t,debug,info,warn,error,fatal}] step 1 นาที
  • ตาราง: rows: LogRow[] (limit 100; ม็อกแสดง 25) · หัวข้อ = error.hint → title ของ eventCode → message · ข้อความเล็กหน้าหัวข้อ = eventCode หรือ logger เมื่อเป็น app.log · ป้าย NEW จาก fingerprint ของ group ที่ isNew · บรรทัด ORA-12899 เป็น ERR เพราะ response ตอบ 500 (SPEC §12 A: บรรทัดที่พักไว้เขียนเป็น error เมื่อ status ≥ 500 ก่อนบรรทัด http.request)
  • chip: http.method, http.route, error.originFunction (source), error.originFile, error.target หรือ dependency.host:port, job.type / id / attempt, fields["dependency.affects"]; บรรทัด error จาก exception filter ไม่มี status และ duration เอง จึงใช้ค่าจากบรรทัด http.request ของ trace เดียวกัน (ดูคำถาม)
  • โหลดเพิ่ม: before=nextBefore · รายการ route ใน select: overview.routes (top 20)
  • ค่าต่อนาทีในกราฟมาจากตารางเดียวกับ Overview และ components.html; ยอดรวมตรงกับ dataset: request ของ /api 70,800, 5xx 112 request (ERR 2 บรรทัดต่อ request = 224 + ECONNREFUSED 3 + job.failed 1 = 228), 4xx 342 request (277 × 404 + 65 × 400, WRN 2 บรรทัดต่อ request = 684 + retry 4 + ThaID 401 4 + still_down 1 + redelivered 1 = 694)
  • แถวตัวอย่าง 25 แถวเลือกมาให้เห็นบรรทัดทุกแบบ ของจริงที่ ~1,700 บรรทัด/นาที 25 แถวล่าสุดจะอยู่ในวินาทีเดียวกัน · เวลา job #88412 ตรงกับ Trace, งานเบื้องหลัง และ Error

การโต้ตอบ

  • Motion: แท่ง histogram โตจากแกนซ้ายไปขวาเมื่อเห็นครั้งแรก · บรรทัดใหม่ (tr.is-new) เลื่อนเข้าด้านบนพร้อมพื้นเขียวอ่อนที่จางใน 1.6 s · จุด "สด" กระพริบช้า ๆ เมื่อช่วงเวลาเป็นแบบล่าสุด · ปิดได้ด้วย ?motion=off หรือ reduced motion
  • พิมพ์แล้ว Enter = ค้น · × บน chip เอาตัวกรองออก · chip Level/Event กดเปิดปิดได้ · ทุกตัวกรองอยู่ใน URL (คัดลอกลิงก์ได้)
  • กราฟ: ชี้เมาส์ดูจำนวนแต่ละ level ของนาทีนั้น · คลิกแท่ง = ซูมเหลือนาทีนั้น · ลากคลุมหลายแท่ง = เลือกช่วงเวลา · "ดูเป็นตาราง" สำหรับคีย์บอร์ดและ screen reader · จอแคบเลื่อนไปนาทีล่าสุดก่อน
  • คลิกแถวหรือหัวข้อ = เปิด drawer ทางขวา (modal: Tab วนอยู่ใน drawer, Esc, ปุ่มปิด หรือแตะพื้นหลังเพื่อปิด แล้ว focus กลับที่แถว) · ลูกศรหน้าแถว = ขยายรายละเอียด error ในแถว (ต้องแก้อะไร / error จริง / trace + user)
  • ลิงก์ trace ไป trace-detail.html · ลิงก์ user กรองหน้านี้ด้วย userId · "ดู error group" ไปหน้าของ group นั้น · "ดู log ทั้ง trace" กรองหน้านี้ด้วย traceId
  • จอแคบกว่า 600 px: แต่ละแถวเป็น 3 บรรทัด (เวลา · level · เวลาที่ใช้ / หัวข้อ หมวด และ chip / service) ตารางไม่ต้องเลื่อนข้าง
  • ม็อกนี้มีรายละเอียด drawer เฉพาะแถว ORA-12899 · หน้าเปิดมาโดยไม่มี drawer ใส่ ?drawer=ora ใน URL เพื่อเปิด drawer นั้นตอนโหลด (focus ไม่ย้าย)

คำถามที่ยังเปิดอยู่

  • status และ duration ของบรรทัด error: ให้ /api/logs join จากบรรทัด http.request ของ trace เดียวกันมาใน LogRow.http.status / durationMs (เสนอใน DESIGN.md §9) หรือ UI ยิง /api/logs?traceId=…&event=http.request เอง
  • pretty format ของ library ยังเขียน path=: หน้าจอใช้ route= ทุกหน้าแล้ว ขอทีม SDK เปลี่ยน key ให้ตรง
  • Raw JSON: เก็บบรรทัดดิบไว้อีกคอลัมน์ หรือประกอบกลับจากคอลัมน์ + labels + fields (ลำดับ key และชนิดข้อมูลบางตัวอาจไม่ตรง เช่น user.roles เป็น array)
  • chip ที่ใช้อยู่ level ≥ INF ซ้ำกับปุ่ม Level: เก็บทั้งสอง (chip สรุปปุ่ม) หรือเก็บแบบเดียว · prod เก็บตั้งแต่ INF (DBG = 0 เสมอ): ซ่อน chip DBG ใน prod หรือไม่
  • ต้องมี live tail (อัปเดตเอง) ไหม: API ตอนนี้ไม่มี streaming
